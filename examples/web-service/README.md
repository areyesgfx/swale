# acme-api

The AWS infrastructure for acme-api, generated by [swale](https://github.com/areyesgfx/swale) from `swale.yaml`.
It's plain Terragrunt and Terraform, and it's yours to edit: swale never overwrites a file that already exists.

## What you get

Everything runs in the `us-east-1` AWS region.
Each environment is a separate copy of the infrastructure, so you can try a change in one without touching the others.

- **stage**: a private network (`10.20.0.0/16`) spread across two availability zones, which are separate data centers in the region.
  Both zones share one NAT gateway, which costs less, but if that gateway's zone goes down, the whole network loses internet access.
  Your app runs as 1 copy.
  Its database is a `db.t4g.micro` instance, and keeps 7 days of backups.
- **prod**: a private network (`10.30.0.0/16`) spread across two availability zones, which are separate data centers in the region.
  Each zone has its own NAT gateway, so if one zone goes down, the other keeps its internet access.
  Your app runs as 2 copies, spread across both zones.
  Its database is a `db.t4g.small` instance with a standby copy in the other zone, which takes over automatically if the first one fails, and keeps 14 days of backups.
  It's protected from deletion, so a mistaken `destroy` can't remove it.

Each network has public subnets, which the internet can reach, and private subnets, which it can't.
Anything running in a private subnet can still reach out to the internet, for example to call an API, through a NAT gateway.

Your app runs in containers on [AWS Fargate](https://aws.amazon.com/fargate/), so there are no servers to manage.
In each environment, [CloudFront](https://aws.amazon.com/cloudfront/) serves your app over HTTPS at an address like `https://d1234abcd.cloudfront.net`, and redirects plain HTTP to HTTPS.
It passes each request, privately, to a load balancer inside the network, which forwards it to your app on port 8080.
Nothing but CloudFront can reach the load balancer, and nothing but the load balancer can reach your app's containers.
CloudFront doesn't cache anything, so your app sees every request, and it adds standard security headers such as HSTS to every response.
The load balancer checks `/health` on each container, stops sending requests to any that don't answer with a 2xx or 3xx status, and ECS replaces them.

Each environment has its own container registry (Amazon ECR) for your app's images, and keeps your app's logs in CloudWatch Logs for 30 days.

Your app has a PostgreSQL 17 database (Amazon RDS) in each environment, in the private subnets, that only your app's containers can reach.
It only accepts encrypted connections, encrypts what it stores, and takes a backup every day.
Your app gets its connection details as environment variables: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME` and `DB_PASSWORD`.
The password was generated by AWS Secrets Manager on the first `apply` and is kept there; it never appears in Terraform state or in this directory.

## What it costs

Most of the network is free, but NAT gateways aren't.
This project has 3 NAT gateways in total.
AWS bills each one by the hour, plus a charge for every GB of traffic it handles and a small hourly charge for its public IP address.
In us-east-1 a NAT gateway is about $0.045 an hour, or around $33 a month before traffic.
Your app's containers are billed while they run: with the defaults, 0.25 vCPU and 0.5 GB of memory each, that's about $9 a month per copy in us-east-1.
Each database is billed by the hour: in us-east-1, about $12 a month for a `db.t4g.micro`, or about $47 for a `db.t4g.small` with a standby copy, plus storage at about $0.12 a GB per month for each copy.
Each environment's database password secret is $0.40 a month.
Each load balancer is about $16 a month in us-east-1, plus a charge that grows with traffic.
CloudFront's free tier covers 1 TB of traffic and 10 million requests a month across the account; beyond that it charges per GB and per request.
Prices vary by region and change over time, so check [Amazon VPC pricing](https://aws.amazon.com/vpc/pricing/), [AWS Fargate pricing](https://aws.amazon.com/fargate/pricing/), [Amazon RDS for PostgreSQL pricing](https://aws.amazon.com/rds/postgresql/pricing/), [Elastic Load Balancing pricing](https://aws.amazon.com/elasticloadbalancing/pricing/) and [CloudFront pricing](https://aws.amazon.com/cloudfront/pricing/) for `us-east-1`.
To stop paying for an environment, tear it down (see below).

## Before you deploy

You need:

- [Terraform](https://developer.hashicorp.com/terraform/install), and [Terragrunt](https://terragrunt.gruntwork.io/docs/getting-started/install/) 1.1.0 or newer.
- Credentials for the AWS account you're deploying to, in the shell you deploy from.
  If you sign in to AWS through a browser (IAM Identity Center), run `aws sso login --profile <profile>`, then `export AWS_PROFILE=<profile>`.
  Otherwise, ask whoever manages your AWS account how to authenticate.

## Deploying

Deploy one environment at a time, starting with stage.
From this directory:

```sh
cd live/stage
terragrunt stack run plan --backend-bootstrap
terragrunt stack run apply
```

`plan` shows what will be created, without changing anything.
`--backend-bootstrap` makes it first create the S3 bucket that stores Terraform state, `acme-api-tfstate-0a1b2c3d`; you only need it the first time.
`apply` creates everything, after asking you to confirm.
The first `apply` in an environment takes 10 to 20 minutes, mostly waiting for CloudFront to deploy worldwide.

Then do the same for the other environments, in this order:

- `live/prod`

### Shipping your app

The first `apply` creates an empty container registry, so your app can't start until you push an image to it.
Find the registry's address in the output of:

```sh
terragrunt stack output
```

It's the `service` unit's `repository_url`, and its `url` is where your app will be reachable.
Then, from your app's directory (the one with the Dockerfile), build your image, push it as version `v1`, and tell ECS to start it:

```sh
REPO=<repository_url>
aws ecr get-login-password --region us-east-1 | docker login --username AWS --password-stdin "${REPO%%/*}"
docker build --platform linux/amd64 -t "$REPO:v1" .
docker push "$REPO:v1"
aws ecs update-service --region us-east-1 --cluster acme-api-stage --service acme-api-stage --force-new-deployment
```

`--platform linux/amd64` matters on Apple silicon Macs, which otherwise build images that Fargate can't run.
Do the same for each environment, with its own `repository_url`, and its own cluster and service name, `acme-api-<environment>`.

To ship a new version, push it under a new tag, such as `v2` or your git commit hash.
A tag can only be pushed once, so it always means the same image.
Then set `image_tag` to the new tag in `live/<environment>/terragrunt.stack.hcl` and run `terragrunt stack run apply` there.
To roll back, set `image_tag` back to the previous tag and apply again.

## Making changes

To change the infrastructure, edit the files under `live/`, `units/` and `modules/`, then run `terragrunt stack run plan` and `terragrunt stack run apply` in each environment you changed.

To add an environment, add it to `environments` in `swale.yaml` (swale knows `dev`, `stage` and `prod`) and run `swale generate`.
It creates the new environment's files and leaves every existing file alone.

Your app starts with no permissions to use other AWS services.
To let it use one, such as S3 or SQS, add an `aws_iam_role_policy` for `aws_iam_role.task` in `modules/service/main.tf`.

The database password never changes on its own, since your app's containers read it only when they start.
To change it, increase `password_version` in `live/<environment>/terragrunt.stack.hcl` and run `terragrunt stack run apply` there, then restart your app so it reads the new one:

```sh
aws ecs update-service --region us-east-1 --cluster acme-api-<environment> --service acme-api-<environment> --force-new-deployment
```

## Upgrading providers

Each `units/<name>/.terraform.lock.hcl` pins the exact Terraform provider builds, so every run on every machine uses the same ones.
Terraform never updates these files by itself.
To upgrade, regenerate one from its module, check that `plan` shows no surprises, and commit it:

```sh
terraform -chdir=modules/networking providers lock -platform=darwin_arm64 -platform=darwin_amd64 -platform=linux_amd64 -platform=linux_arm64 -platform=windows_amd64
mv modules/networking/.terraform.lock.hcl units/networking/
```

## Tearing an environment down

```sh
cd live/<environment>
terragrunt stack run destroy
```

This deletes everything in that environment.
The state bucket and the state in it are kept, so you can deploy the environment again later.

Before deleting a database, RDS takes a final snapshot of it, named `acme-api-<environment>-final`, which you're billed for until you delete it.
Delete it in the RDS console before destroying that environment's database again, since the name must be unique.
prod's database is protected from deletion: set `deletion_protection = false` in `live/prod/terragrunt.stack.hcl` and apply before destroying it.

## What's in this directory

- `swale.yaml`: your answers to `swale init`.
- `root.hcl`: settings every environment shares: where Terraform state is stored, the AWS region, and tags added to every resource.
- `live/<environment>/terragrunt.stack.hcl`: what each environment contains, and its settings.
- `units/`: how each piece of infrastructure is wired into an environment.
- `modules/`: the Terraform code for each piece, copied into this project so it doesn't depend on anything outside it.
